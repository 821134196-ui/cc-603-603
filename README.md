# 城市地铁闸机故障票务补登系统

一次闸机故障会派生**两类工单**：维修工单（维修员修设备）与票务工单（客服处理乘客缺失行程与差价）。两类工单在受理页并列展示进度、**各自独立结案**：设备修好不会自动关闭乘客问题，乘客问题处理完也不会让未修复的闸机从告警看板消失。

## 一条命令启动

```bash
npm start
```

该命令依次完成：安装依赖 → Prisma 初始化 SQLite（`server/prisma/dev.db`）并播种闸机 → 同时启动后端（http://localhost:3000/api）与前端（http://localhost:5173）。

```bash
npm test        # 运行核心不变式的端到端验证（12 个用例）
```

## 技术栈

- **后端**：TypeScript + NestJS（`server/`），Prisma + SQLite（两类工单及各业务表）
- **前端**：React + Vite（`web/`），`/api` 代理到后端
- **本地模拟**：闸机日志（`/api/logs/simulate` 生成报文、`/api/logs/upload` 上传）与支付回执（扣费/退款均落 `PaymentReceipt`）

## 角色与流程

1. **站务员**在「受理页」登记故障闸机与发生时间 → 同事务生成维修工单 + 票务工单，闸机进入告警看板。
2. **维修员**在受理页「开始维修 → 确认修复」→ 仅推进维修工单并恢复设备，闸机从告警看板撤下（唯一撤板途径）。
3. **客服**在「票务处理」复核晚到记录 → 补登出站（自动核算票价、多扣即退差价）或人工退款 → 票务工单结案。
4. 「告警看板」保留设备异常提示，直到维修确认完成；「退款与回执」可审计每笔退款。

## 关键设计（不变式）

| 需求 | 实现 |
| --- | --- |
| 同一日志重复上传只形成一次有效记录 | `GateLog.contentHash` 唯一（SHA-256），命中即整体拦截，不产生任何新记录 |
| 不能生成两段相同行程 | `TripRecord.dedupeKey`（卡号\|进站站点\|进站时间）唯一，重叠日志逐条去重 |
| 故障期间晚到的刷卡记录须复核 | 记录落在故障时间窗（发生时间 ~ 维修确认）内 → `NEEDS_REVIEW`，复核后才能补登 |
| 一趟行程最多退款一次 | `Refund.tripId` 唯一 + 服务层预检 + P2002 兜底（409） |
| 两类工单分别结案、互不影响 | 维修确认只动 `RepairOrder`+闸机状态；票务结案只动 `TicketOrder`，且有未处理行程时 409 拦截 |
| 看板保留异常直到维修确认 | 告警看板以 `Gate.status=FAULT` 为准，仅维修确认（`RESOLVED`）可恢复 |

## 验证（`server/test/app.e2e-spec.ts`，12 个用例全绿）

- **A 组**：重复上传同一日志 → 行程数/退款数不变；重叠日志只新增新行程；补登退差价只退一次；重复退款 409。
- **B 组**：票务结案不撤告警、不动维修工单；维修确认不改变票务工单；设备修好后未处理行程仍挡住票务结案。
- **C 组**：晚到记录未复核不能补登、挡住结案；复核→补登→结案后，未修复闸机仍在告警看板。

## 目录结构

```
├── package.json          # npm workspaces，npm start 一条命令
├── server/               # NestJS + Prisma
│   ├── prisma/schema.prisma  # 两类工单、日志、行程、退款、回执
│   ├── src/              # incidents / logs / trips / orders / dashboard 模块
│   └── test/app.e2e-spec.ts  # 核心不变式验证
└── web/                  # React + Vite（受理页/告警看板/票务处理/日志模拟/退款回执）
```
